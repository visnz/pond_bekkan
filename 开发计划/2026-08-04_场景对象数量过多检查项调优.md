# 2026-08-04 · 「场景对象数量过多」检查项调优

## 1. 目标与背景

`check_object_count`（`core/analyzer/checks.py`，`STRUCT.object_count`）只报一个笼统的
总对象数，不告诉用户负载具体在哪。用户在实际项目里踩过三类坑：

1. 某个集合里堆了几百个物体（尤其带层级嵌套时更隐蔽）。
2. 一个物体被几何节点炸成几千个虚拟实例——总数检查能测到，但看不出「元凶」是谁。
3. 毛发/粒子系统的 Child（子级）数量把粒子数放大好几倍，肉眼看不出来。

这轮新增 4 个更具体的检查项，各自定位到「哪个集合/哪个物体/哪个粒子系统」，全部是
`EASE_HARD`（结构性问题，没有安全的自动修复默认值），只加检查、不加修复按钮。

全部改动限定在 Bekkan 专属的 `core/analyzer/checks.py`；`model.py`/`fixes.py`/`ops.py`/
`ui/bekkan/analyzer_panel.py` 均未改动（无自动修复，走现有「暂无可用的自动修复」兜底分支）。

## 2. 改动内容

### 新增 `_scene_objects(context)`

替代新检查里用的 `_objects()`（全局扫 `bpy.data.objects`，不分 Scene）。`_scene_objects`
返回 `context.scene.objects`，天然只含当前场景链接的对象——用户明确要求「不在当前 scene
的集合不纳入计算」。`check_object_count` 本身未改（超出本轮范围，仍用 `_objects()`）。

### `_collection_object_total(coll, _depth=0)`

新增的集合递归对象总数辅助函数，供检查 1、2 共用。同一集合被多个父集合链接时两处都算数
（这是真实渲染负载），只加深度上限 50 防御异常数据，不做去重。

### 简单检查（`_QUICK_CHECKS`，紧跟 `check_object_count` 之后）

| key | 说明 | 阈值 |
|---|---|---|
| `STRUCT.dense_collections` | 递归遍历当前场景集合树，列出对象数过多的集合（📦/⚠ 图标标记），末尾附带跨 Scene 提醒 | ≥200 列出，≥500 重点 |
| `STRUCT.collection_instance_multiplier` | 按 `instance_collection` 分组统计集合实例 Empty 引用次数 × 集合对象数 = 实际渲染负载 | load≥2000 列出，≥10000 重点 |
| `STRUCT.particle_heavy` | 遍历粒子系统，`count × child_mult` 估算真实粒子/毛发数，Object/Collection 渲染追加放大提示 | ≥1000 列出，≥10000 重点 |

### 深度检查（`_DEEP_CHECKS`）

| key | 说明 | 阈值 |
|---|---|---|
| `STRUCT.geonode_instances` | 遍历一次 `depsgraph.object_instances`，按 `inst.parent.original.name` 归堆几何节点/实例生成的虚拟实例；附带全场景实例总数远高于对象数的兜底提示 | 单源≥200 列出，≥2000 重点 |

### 跨 Scene 提醒

`check_dense_collections` 顺带算一次 `len(_objects()) - len(_scene_objects(context))`，
差值 >200 时在 detail 末尾追加提示，不单开检查项，不深入分析其他 Scene 内部结构。

## 3. 待验证的风险点（用户 GUI 实测时重点核对）

1. **粒子 Child 属性名是否命中**：`rendered_child_count` / `child_nbr` 两个候选属性名
   （抄自 `check_sampling` 的多候选写法）在离线环境无法验证是否命中当前 Blender 5.2 版本，
   若都不存在则乘数退化为 1（不放大），需要用真实毛发/粒子物体测试核对倍数是否符合预期。
2. **`inst.parent` 语义是否符合预期**：`depsgraph.object_instances` 遍历里用
   `inst.parent.original.name` 归堆几何节点生成的实例源物体，这个字段在离线环境无法验证，
   需要用已知会炸出几千实例的几何节点物体实测，核对计数是否落在正确的源物体名下；
   若不可用，仍应保留「总实例数远高于对象数」的兜底提示（不会静默报空）。
3. **简单/深度检查划分是否需要调整**：3 个简单检查目前都是静态属性读取（集合计数、
   实例分组、粒子设置数量），按现有 `check_viewport_only` 的 depsgraph 预算先例判断
   应该足够快；这只是第一版分工，若大场景下测出某个简单检查明显变慢，需要单独反馈后
   再挪到深度检查，这轮未预先拆两套实现。

1. **`check_dense_collections` 合并回 `check_object_count`**：用户认为「集合对象过多」

4. **修复「限制4K/限制2K」贴图钳制按钮没有效果的 bug**：`fixes.fix_clamp_textures` 之前
   只设置了 `cycles.texture_limit`，但 Blender 的「简化」面板里这项设置**只有总开关
   `scene.render.use_simplify` 打开时才会真正生效**——之前完全没碰这个开关，所以设置
   值本身正确但从不生效。修复：额外设置 `context.scene.render.use_simplify = True`；
   `ops.py` 的成功提示也补充说明「已开启简化总开关」，方便用户理解为什么现在有效果了。
5. **通用 UI 改进**：`_draw_detail`（`ui/bekkan/analyzer_panel.py`）里「问题详情」「处理
   手段」两块现在也各自包一层 `box.box()`，和已有的「快速修复」框视觉对齐，三个区块
   更容易分辨。

## 7. 用户第二轮实测反馈的修正（同日）

用户 GUI 实测后又提出四点，本节记录修正：

1. **彻底移除「定位到集合」功能**：用户反馈这个按钮实际用不上（"没办法快速定位到集合，
   这个就不要了，让用户自己定位吧"）。删除 `core/analyzer/ops.py` 里的
   `ANALYZER_OT_locate_collection` 操作符类与 `_find_layer_collection` 辅助函数、
   `core/analyzer/__init__.py` 里对应的 import 与 `_CLASSES` 注册项、
   `ui/bekkan/analyzer_panel.py` 里 `_draw_locator_buttons` 对 `STRUCT.object_count`
   的专属分支——现在这个 key 和 `MAT.big_textures`/`MAT.texture_clamp` 一样，统一走
   「没有可用的定位/选中方式，用户需自行在大纲里找」的跳过分支，不显示任何按钮。
2. **修复「排除的集合仍被计入对象过多统计」的 bug**：根因是 `_dense_collection_rows`
   之前沿 `context.scene.collection`（数据层级树）递归，完全不知道 View Layer 的
   排除（exclude from view layer）状态。改为沿 `context.view_layer.layer_collection`
   （View Layer 树）递归，遇到 `layer_coll.exclude` 为真的分支直接整棵跳过（不计数、
   不列出）——被排除的集合根本不参与该 View Layer 的求值，谈不上拖慢视口/渲染。
   新增 `_layer_collection_object_total(layer_coll)` 作为该场景下「排除感知」的递归总数
   计算，专供这个检查使用；`_collection_object_total(coll)`（数据层级递归，不感知排除）
   保留不变，因为 `check_collection_instance_multiplier` 统计的是被 Empty
   `instance_collection` 引用的集合，这类集合本身未必挂在当前 View Layer 树上，
   谈不上「排除状态」，不能套用同一套逻辑。
3. **纹理限制改为同时影响视口与渲染**：`fixes.fix_clamp_textures` 之前只设置
   `cycles.texture_limit`（视口），现在额外设置 `cycles.texture_limit_render`（渲染），
   两者都由同一个「简化」总开关 `use_simplify` 控制生效。同步更新了
   `check_texture_clamp` 的建议文案、`ops.py` 的成功提示、面板 `MAT.big_textures` /
   `MAT.texture_clamp` 两处按钮说明文字，全部改为「同时钳制视口与渲染」的表述，
   不再有"仅影响 Cycles 视口"这类过时描述。
4. **新增「细分级数过高」检查**（用户新提出的场景，评估后确认计划里没有，新增）：
   `core/analyzer/checks.py` 新增 `check_subdivision_high`（key `GEOM.subdivision_high`，
   `_QUICK_CHECKS` 简单检查）。遍历当前 Scene 内网格对象的 `SUBSURF`/`MULTIRES`
   修改器，视口 `levels`/渲染 `render_levels` 取较大值，≥3 即列出（分别尊重
   `show_viewport`/`show_render` 开关，关闭的一侧不计入）；影响程度按最高级数是否
   ≥5 分 `IMPACT_HIGH`/`IMPACT_MED`，`ease = EASE_HALF`，`category = CATEGORY_STRUCTURE`
   （沿用 `GEOM.high_poly_count` 的类别搭配，key 前缀与 category 不必一致，是本项目
   既有惯例）。修复逻辑与纹理限制同思路：新增 `fixes.fix_cap_subdivision`，通过
   「简化」面板的 `render.simplify_subdivision`（视口上限）+
   `render.simplify_subdivision_render`（渲染上限）钳制全场景细分级数上限并开启
   `use_simplify`，不改各修改器自身的级数值。面板加了「限制到 2 级」/「限制到 1 级」
   两个按钮（`ops.py` 按 `self.option` 转 int 调用）。这个 Finding 的 `obj_names` 是
   真实的对象名（不是集合名/贴图名），沿用现有通用「选中相关对象」按钮，未加入跳过名单。

## 8. 用户第三轮实测反馈的修正（同日）

用户 GUI 实测后又提出六点，本节记录修正：

1. **修复 `check_merge_same_material` 崩溃**：报错「Object of type 'Object' has no
   len()」。根因是 `collect_merge_same_material_groups` 返回 `[[obj, obj, ...], ...]`
   （已经是「对象列表的列表」），但 `check_merge_same_material` 里
   `top = max(cands, key=lambda x: len(x[1]))` 的 `x` 本身已经是某一组的对象列表，
   `x[1]` 取到的是该组第二个 `Object`，对它调 `len()` 必然崩。改成
   `top = max(cands, key=len)`，直接按每组对象数取最大组。
2. **`check_persistent_data` 改为单向触发 + 一键开启**：原来「已开启」也会生成一条
   Finding（描述成问题在提示，且用户已经手动开启了还在报），违反「检测=问题」的
   直觉。删掉「已开启」分支，`check_persistent_data` 现在只在**未开启且场景较大**时
   触发，标题改为「未开启保留数据（建议开启）」；配套把 `fixes.fix_toggle_persistent_data`
   （取反逻辑）改名重写为 `fix_enable_persistent_data`（只做「开启」这一个动作，
   已开启时返回 skip），`ops.py`/`analyzer_panel.py` 两处按钮文案同步改为
   「开启保留数据（Persistent Data）」。
3. **模式标签加耗时提示**：`core/analyzer/props.py` 的 `AnalyzerProps.mode`
   EnumProperty 两个选项标签改为「简单检查（几秒）」「深度检查（几分钟）」，
   让用户运行前就有预期。
4. **`check_light_count` 按引擎分别给建议**：原来无论引擎都直接读
   `scene.cycles` 属性（Light Tree / 阴影剔除），违反 CLAUDE.md 明确警告的
   「`scene.cycles`/`scene.eevee` 永远不为 None，不能当引擎判断依据」——这正是
   用户反馈「建议看起来都是 eevee 的」的根因（EEVEE 场景下也会读到 Cycles 专属建议）。
   改为先 `eng = _engine(context)` 判断，Cycles 分支保留 Light Tree / 阴影剔除建议，
   新增 EEVEE 分支给出 Light Linking / 关闭次要灯光阴影投射 / 检查阴影池大小的
   针对性建议，未识别引擎时保留原通用建议兜底。
5. **`check_sampling` 噪点阈值四舍五入 + 区分视口/渲染阈值**：原来
   `detail.append(f"噪点阈值过低（{th}）")` 直接拼未处理的浮点数，会显示成
   `0.00999999999999776` 这种丑陋值；而且只读了 `cycles.adaptive_threshold`
   （渲染阈值）一个属性，没区分视口（预览）阈值。改为：显示值统一
   `round(th, 3)`（保留 3 位小数，即最小可显示精度 0.001）；分别检查
   `cycles.adaptive_threshold`（渲染，<0.02 触发，建议调到 0.02~0.04）与
   `cycles.preview_adaptive_threshold`（视口，<0.05 触发，建议调到 0.1 左右，
   `hasattr` 防御跨版本缺失）。配套把 `fixes.fix_adaptive_sampling` 改为把
   渲染阈值调到 0.03、视口阈值调到 0.1（用户指定的目标值），
   `analyzer_panel.py` 的 `RENDER.sampling` 修复按钮文案改为
   「自动调整（视口 0.1 / 渲染 0.03）」。
6. **详情面板文本不可复制的问题**：确认这是 Blender 平台限制——`UILayout.label()`
   渲染的文本在 N 面板里本身无法像文本编辑器那样框选复制，插件没有绕过的办法。
   给出的变通方案：新增 `analyzer.copy_names_visn` 操作符
   （`core/analyzer/ops.py`），把 `item.obj_names` 整份写入
   `context.window_manager.clipboard`；`_draw_locator_buttons`
   （`ui/bekkan/analyzer_panel.py`）现在**始终**在有 `obj_names` 时显示
   「复制名称到剪贴板（N 个）」按钮（哪怕是 `STRUCT.object_count` 等没有安全选中
   方式的 key，复制按钮依然可用），方便用户粘贴到大纲视图的搜索框按名字过滤查找。
   操作符已加入 `core/analyzer/__init__.py` 的 `_CLASSES` 注册表。

### 问题描述

的就是这类问题）遇到的是同一类 bug，要求顺带排查工程分析模块里其他操作是否也有
同类问题。

### 根因

`analyzer.fix_visn`（`ANALYZER_OT_fix`）的按钮画在 3D 视口 N 面板（别馆分类）里，
但它的各个 `fix_*` 分支基本都是直接对 `scene.render`/`scene.cycles`/`scene.eevee`
或对象可见性属性赋值（`fix_adaptive_sampling`、`fix_cap_bounces`、
`fix_clamp_textures`、`fix_cap_subdivision`、`fix_enable_persistent_data`、
`fix_disable_motion_blur`、`fix_shadow_pool`、`fix_device_gpu`、
`fix_output_compression`、`fix_light_perf_toggles`、
`fix_viewport_to_render_visible`/`_hidden` 等）。这些属性显示在属性编辑器的
渲染/输出/对象标签页，或大纲视图里——都不是按钮所在的那个 3D 视口区域。Blender
只会重绘触发 operator 的那个区域，不会自动重绘其它编辑器；纯 Python 属性赋值也
不总能触发足以让其它编辑器重绘的通知，于是就是用户看到的"数据改了但面板没更新，
切一下标签页/引擎才刷新"。

项目里已经有解决同类问题的现成写法：`core/addonmanager/common.py` 的
`update_list_filter`（"强制 UI 刷新 (覆盖所有可能包含列表的窗口和区域)"）—— 遍历
所有窗口的所有区域调用 `area.tag_redraw()`，不限区域类型。这次直接复用这个思路。

### 改动内容

- 新增 `_tag_redraw_all(context)`（`core/analyzer/ops.py`），遍历
  `context.window_manager.windows` 下所有 `window.screen.areas` 调用
  `area.tag_redraw()`，不区分区域类型（因为修复动作可能影响渲染/输出/对象属性页
  或大纲视图，具体是哪个不确定，直接全刷比逐一判断类型更省心也更稳）。
- 在 `ANALYZER_OT_fix.execute()` 末尾唯一的 `return {'FINISHED'}` 前调一次

- `object.parent_to_empty_anim_visn`（`core/hierarchy.py`）是 Mixed 模块，同类问题

### 12.4 修复：Cycles 渲染设备为 NONE 时检测不出"未使用 GPU"

用户实测反馈：当前 Cycles 设备是 `NONE`，但"渲染设备未使用 GPU"这条建议没有出现；并要求
如果检测到多种后端可用，优先推荐 OptiX（NVIDIA 显卡上通常比 CUDA 快）。

- 根因：`_has_available_gpu()`（旧实现）判断逻辑是"遍历 `preferences.devices`，找
  `type == 当前 compute_device_type` 且 `use=True` 的设备"。但如果用户从没在
  Preferences 里手动打开过 GPU 计算，`compute_device_type` 本身就是 `'NONE'`，这个循环
  永远找不到 `type == 'NONE'` 的设备（真实 GPU 设备的 type 是 `'CUDA'`/`'OPTIX'` 等），
  于是永远返回 `False`——完全漏检了"机器上有 GPU 但从没配置过"这种最常见的情况。
- 修复：新增 `_detect_gpu_backend()`，用 Cycles 偏好设置提供的 `get_devices_for_type()`
  API 主动探测每个后端（不依赖也不改动当前选中的 `compute_device_type`），按
  `OPTIX > CUDA > HIP > ONEAPI > METAL` 优先级返回第一个探测到设备的后端。
  `check_device` 改用这个函数，Finding 里带上探测到的后端名和设备名。
- 连带修复 `fix_device_gpu`：旧实现只设置 `scene.cycles.device='GPU'`，如果
  `compute_device_type` 仍是 `'NONE'`，Cycles 会静默退回 CPU 渲染——界面显示"已修复"但
  实际没用上显卡。现在修复时会同时把 `compute_device_type` 切到探测到的后端，并把该
  后端下的设备逐个 `use=True`，效果等同于手动去 Preferences 里勾选。
