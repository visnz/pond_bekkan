# 2026-08-04 · analyzer「场景对象数量过多」双口径 + 几何节点实例放大汇报

## 1. 目标与背景

用户实测反馈：一个工程里只有 1 个物体，通过几何节点分布了一万多个实例对象，
Blender 视口统计（Objects）显示两万多，但当前 `check_object_count`
（`STRUCT.object_count`）只报「物体过多，2400 个」——因为它只数 `bpy.data.objects`
的真实对象，几何节点/集合实例生成的**虚拟实例**不在 `bpy.data.objects` 里，被完全漏掉，
严重低估了实际渲染/导出负载。

用户要求：
1. 给对象数量提供**两种统计口径**：口径一 = 当前这种（真实对象）；口径二 = 含实例
   （Blender 自带视口统计那种，几何节点/集合实例生成的虚拟实例也计入）。
2. 把「几何节点产生巨量实例」这种情况**点名汇报**（哪个物体产生多少个），
   并推动用「实例化 + 烘焙」解决。

全部改动限定在 Bekkan 专属的 `core/analyzer/`：`checks.py`、`ops.py`、`fixes.py`（docstring）。
未动 `model.py`/`props.py`/`state.py`/`ui/bekkan/analyzer_panel.py`。

## 2. 改动内容

### 2.1 `core/analyzer/checks.py`

**新增 `_instance_stats(context)` 助手**：遍历 `context.evaluated_depsgraph_get().object_instances`
一次，返回 `(real, inst, per_source, total_eval)`：
- `real`：非实例条目数（当前场景真实对象）
- `inst`：实例条目数（几何节点/集合实例的虚拟实例）
- `per_source`：按 `inst.parent.original.name` 归堆的实例数（定位"元凶"）
- `total_eval = real + inst` ≈ Blender 视口统计的 Objects 数

depsgraph 在交互场景下通常已求值，遍历只读 O(实例数)，不额外触发重算；
异常时返回 `(0,0,Counter(),0)` 兜底（调用方按未放大处理）。

**`check_object_count` 双口径改造**：
- 触发条件新增 `amplified = n_inst >= 1000`：`if n < 3000 and not rows and not amplified: return None`。
- detail 里报两个口径：口径一「当前真实对象共 N 个」；放大时追加
  「按 Blender 统计口径（含实例）共约 T 个，其中虚拟实例约 I 个，来自：」+ 前 5 个来源。
- count 在放大时改为 `total_eval`（列表 × 显示真实负载，不再停留于 2400）。
- impact 在 `total_eval > 20000` 时升 `IMPACT_HIGH`。
- suggestion 在放大时追加「实例化到点上 / 烘焙」建议。
- 保持只报一条 Finding（沿用"同一件事合成一条"的项目惯例），不放新 key。

**`check_geonode_instances` 复用 `_instance_stats`**：删除内联的 depsgraph 遍历，
改为 `_, _inst, per_source, total_eval = _instance_stats(context)`，行为等价
（`total_eval` 仍为全部条目数，per_source 归堆逻辑不变）。避免两份相同遍历漂移。

### 2.2 `core/analyzer/ops.py`

**`_int_option(self, default)` 防御**：`MAT.big_textures`（改前 `int(self.option)`，
默认 2048）与 `GEOM.subdivision_high`（默认 2）两个分支改用它，option 为空/非数字时
回退默认值，不再被外层 except 吞成「修复失败」。

### 2.3 `core/analyzer/fixes.py`

**`fix_merge_same_material` docstring 如实化**：原 docstring 声称「对
Finding.obj_names 里的对象重新分组」，但实现是点击时从当前数据全局重分组、合并
当前 View Layer 内所有同材质组，obj_names 只是列表定位不是白名单。docstring 改为
描述真实行为，并注明"点击时场景可能已变、从当前数据重算"的取舍。**未改代码行为**
（保留点击时重算的健壮性；如后续希望改成"只修 obj_names 指向的那组"，改动很小）。

## 3. 设计取舍（供用户确认）

- **触发阈值**：`n_inst >= 1000` 才报放大。1 个 GN 物体炸上万实例 → 命中；
  正常小场景的少量实例不会触发。阈值是经验值，可在实测后调整。
- **口径二的来源**：`depsgraph.object_instances` 总数 ≈ Blender 视口统计的 Objects 数
  （含几何节点/集合实例虚拟实例），与用户"blender 自带的统计"对齐。
- **count 语义**：放大时列表 × 显示 `total_eval`（真实负载）；detail 里两个口径都有。

## 4. 验证

- `python -m compileall -q .` → exit 0。
- `python build.py` → 4 个 zip 正常产出（combined/pond/bekkan 各 63 文件，analyzer 11 文件）。
- Blender 后台逻辑验证（`blender --background --factory-startup`，临时 bootstrap 直接
  import `analyzer.checks`）：
  - `_instance_stats` 默认场景 → `(3, 0, Counter(), 3)` 正常。
  - `run_quick` 默认场景 → 3 条，不崩。
  - `run_deep` 默认场景 → 3 条（无实例时 `geonode_instances` 正确 None），不崩。
  - `check_object_count` 用 mock `_instance_stats`（2400/20000/22400）验证放大路径：
    `count=22400`、`impact=较高`、detail 含「Blender 统计口径（含实例）…来自：」+
    来源名、suggestion 含「烘焙」——断言全过。
  - 小场景（无放大）→ 正确返回 None。
- 注意：`tools/test_analyzer.py` 的 CLI 方式（`blender --background --python ...`）
  仍会全部报 `attempted relative import with no known parent package`——这是**既有的
  测试入口问题**（脚本以 `__main__` 运行、没有包上下文，相对 import 无法解析），
  与本次改动无关，T1-T7 需要换成能进包上下文的跑法（如脚本编辑器内运行 / 先插
  sys.path 再 `import pond_bekkan.tools.test_analyzer`）。

## 5. GUI 实测留给用户

1. 打开那个 GN 分布上万实例的工程，跑简单检查：确认 `STRUCT.object_count` 的
   × 数量现在是含实例的大数（不再停在 2400），详情里能看到「当前真实对象共 N 个」
   与「按 Blender 统计口径（含实例）共约 T 个…来自：分布物体」两段。
2. 对比 Blender 视口统计的 Objects 数，确认口径二数字对得上。
3. 点建议里的「实例化到点上 / 烘焙」指引，确认提示文案合理。
4. 回归：普通大场景（真实对象多、无实例）仍只报真实对象口径，行为不变。
5. 顺带回归：`MAT.big_textures`「限制4K/2K」与 `GEOM.subdivision_high`「限制2/1级」
   按钮点击正常（option 防御生效）。

## 5.5 修复：`icon='JOIN'` 崩溃（D1 类，同日补充）

用户跑完深度检查、展开 `STRUCT.merge_same_material` 详情时，面板 draw 抛
`TypeError: UILayout.operator(): error with keyword argument "icon" - enum "JOIN" not found`。
`JOIN` 不在 Blender 5.2 合法图标枚举里（项目已知 D1 坑，但这一处漏用了 `_icon()` 防御）。

- 修复：`ui/bekkan/analyzer_panel.py` `_draw_fix_buttons` 的 `STRUCT.merge_same_material`
  分支 `icon='JOIN'` → `icon=_icon('JOIN')`（`_icon` 查不到 JOIN → 回退 `'NONE'`）。
  该面板是 analyzer 独立版生成的唯一源，此改动随 build 一并进独立版。
- 排查确认全面板仅此一处裸写非法图标（其余 `icon='...'` 字面量逐一核对都在合法枚举内）。
- 为何 D1 测试没拦住：`tools/test_analyzer.py` T3 的面板 draw 只走当前 findings 能触达的
  分支，`merge_same_material` 是深度检查，工厂场景 run_quick 不会产生该条 → 分支没被走到；
  且 CLI 入口（相对 import）本身跑不起来。已在 §6 TODO 记测试入口问题。
