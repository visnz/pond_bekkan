# 2026-10-27 新增搭建类功能：锚点到顶部中心 / 锚点到底部中心

## 目标

用户需求：在「🏗 搭建类」面板加两个按钮——「锚点到顶部中心」「锚点到底部
中心」，把所选物体的原点批量移到各自包围盒的顶/底中心。关键要求：按物体
当前实际的旋转/缩放表现算边界，不能用 p=0/s=1/r=0 标准姿态下的包围盒。

## 跨边界说明

`core/stage.py` 是 Mixed 共同维护文件，本次只新增两个独立 operator
（`StageAnchorTop` / `StageAnchorBottom`）+ 一个共享辅助函数，不碰文件内
任何已有函数/类，不影响 Pond 侧 UI/行为。只在 `ui/bekkan/panels.py` 的
「搭建类」面板加一行两个按钮。用户要求先出原型测试，测试通过后才 commit，
整个过程没有额外走方案确认（改动模式与之前几次新增搭建类按钮一致）。

## 实现与一次返工

### 第一版（有问题，未 commit 就被用户发现）

最初照抄 `core/organize.py` 的 `POND_OT_origin_bottom` 写法：取物体**局部
空间**包围盒 `obj.bound_box` 的 8 个角点，整体乘 `matrix_world` 换到世界
空间，再在这 8 个变换后的点里取 min/max。

用户实测反馈：结果比视觉上的顶/底更宽。

### 根因

局部 AABB（`bound_box`）本身就是比圆柱、不规则 mesh 等非箱形物体更宽松的
包围（比如一个圆柱的局部 AABB 是个方盒，角上是空的）。物体没有旋转时，
把这个盒子的 8 个角点直接搬到世界空间，恰好还是最终形状的真实边界。但
物体一旦被**旋转**，这个本来就偏大的盒子会被整体转个角度——相当于「盒子
套盒子」，转出来的新包围范围只会比真实形状的世界空间范围更大，顶部更高、
底部更低，这就是用户看到的「比视觉更宽」。

### 第二版（修复，已验证）

改成直接取物体的**真实几何控制点**，逐个（不是整体）变换到世界空间，再在
这些点上求 min/max：
- `core/stage.py` 新增 `_world_points(obj)`：
  - `MESH`：遍历 `obj.data.vertices`，每个顶点 `matrix_world @ v.co`。
  - `CURVE`：遍历 `obj.data.splines`。贝塞尔样条（`BEZIER`）同时算进两端点
    和两条手柄（`handle_left` / `handle_right`）——贝塞尔曲线段必然落在
    这四个控制点的凸包内，只看端点会漏算手柄拉出去的那部分曲线形状；
    非贝塞尔样条（NURBS/POLY）遍历 `spline.points`（4 分量，截取前 3 维）。
  - 按用户确认，只处理 `MESH` 和 `CURVE`，其余类型（灯光/摄像机/空物体等）
    不在 `_ANCHOR_TYPES` 里，直接跳过。
- `_anchor_to_bbox(context, objs, pick_z)`：对每个符合类型的物体调
  `_world_points`，XY 取世界空间范围的中点（`(min+max)/2`，不是顶点算术
  均值——均值会被顶点密度不均带偏，比如一端顶点特别密集就会把中心拽偏），
  Z 按 `pick_z`（`max` 或 `min`）取顶或底；然后挪 3D 游标到这个点、调用
  `bpy.ops.object.origin_set(type="ORIGIN_CURSOR")`，和 `core/organize.py`
  的 `POND_OT_origin_bottom` 同一套手法（选中状态、游标位置用完都还原）。
- `StageAnchorTop` / `StageAnchorBottom`：分别传 `max` / `min` 给
  `_anchor_to_bbox`，`REGISTER, UNDO`；一个都没处理到（比如全选非几何物体）
  时 report WARNING + CANCELLED，正常处理后 report 处理了几个物体。
- `ui/bekkan/panels.py`：「搭建类」面板新增一行两个并排按钮。

## 测试

用户当前 Blender（5.2.3 LTS）已通过 MCP for Blender 连接，直接在用户的
真实工作场景（含骨骼绑定等既有物体，56 个物体）里用临时集合
`TMP_anchor_test` 建测试物体，测完整体删除，没碰场景原有任何物体：

1. **数值对照**（旧方法 vs 新方法）：一个圆柱（局部 AABB 是方盒），位置
   `(10,10,1.5)`，旋转 `(0.7, 0.4, 0.3)`，缩放 `(1, 2, 0.5)`：
   - 旧方法（局部 bbox 角点整体乘 matrix_world）：`zmax=3.6045`，
     `zmin=-0.6045`。
   - 新方法（真实顶点逐个变换）：`zmax=3.2738`，`zmin=-0.2738`。
   - 差异 `0.33`——验证了用户反馈的"比视觉更宽"确有其事，且量化出了偏差
     大小。
2. **端到端 operator 调用**（物体模式下，走真实 `select_all` +
   `origin_set` 流程）：
   - `anchor_to_top_visn`：圆柱新原点世界坐标 `(10, 10, 3.2738)`，与真实
     顶点算出的 `zmax` 完全一致。
   - `anchor_to_bottom_visn`：圆柱新原点世界坐标 `(10, 10, -0.2738)`，与
     真实顶点算出的 `zmin` 完全一致。
   - 两次调用之间排查出一次假阳性：中途用户切到了编辑模式，
     `bpy.ops.object.select_all` 的 object-mode poll 失败报错——这是测试
     环境的外部状态（用户当时在编辑别的物体），不是 operator 本身的 bug，
     确认后用正确的 context/选中状态重跑即通过。
3. **曲线手柄验证**（纯计算校验，未过完整 operator——测到这一步时用户
   进入了编辑模式，没有勉强切换用户的模式去跑完整流程）：一条两点贝塞尔
   曲线，`p0.handle_left.z=-2`（局部），`p1.handle_right.z=5`（局部），
   两端点 z 分别是 0 和 3。直接验证 `_world_points` 的计算逻辑：取到的世界
   Z 范围是 `[-2, 5]`，而不是只看端点的 `[0, 3]`——确认手柄被正确计入边界，
   没有漏算手柄拉出去的那部分曲线形状。
4. 测试数据全部清理（临时集合 + 其中的物体/网格/曲线数据块），清理后确认
   `TMP_anchor_test` 不再存在、场景里没有残留 `Test*` 命名的物体，用户当前
   编辑模式下的工作对象未受影响。

用户确认测试通过后提交。

## 已知限制 / 未覆盖

- 曲线分支没有跑完整的「选中→点按钮→原点真的移动」端到端流程（受限于
  测试时用户处于编辑模式，没有强制切换打扰用户），只验证了核心边界计算
  逻辑。`_anchor_to_bbox` 对 MESH 和 CURVE 走的是同一段代码路径，MESH 分支
  已经完整端到端验证过，风险可控，但如果后续发现曲线类型有问题，先查
  `_world_points` 的 `CURVE` 分支。
- 非贝塞尔样条（NURBS/POLY）的 `spline.points` 分支没有单独测试（项目里
  这类曲线使用场景较少），实现上直接取控制点坐标，没有额外处理 NURBS 的
  权重/阶数对实际曲线形状的影响——如果控制点本身就在凸包内（NURBS 曲线
  通常如此），实际边界会比取到的更紧，不会比视觉更宽，方向上是安全的。
