# 2026-08-04/05 · 贴图强制压缩向导 + 「✨ 灯光合成」面板

## 1. 目标与范围

`MAT.big_textures` 现有修复 `fix_clamp_textures` 只在 Cycles 下可用（设
`scene.cycles.texture_limit` 硬钳制）；EEVEE 没有 `texture_limit`，只能真的缩放图片数据。

需求（经用户多轮细化）：
- 单开别馆顶层面板「✨ 灯光合成」作为**新操作脚本容器**，最上层**只有一个按钮**
  「贴图强制压缩」（像上下级面板里的按钮那样）。
- 点击后是**多步向导弹窗**：
  0. 检测报告：多少张 >4K / >2K 贴图
  1. 保存提示（工程带 `*` 脏标记时）：先保存才能运行
  2. 选项：「覆盖原图 / 备份在文件旁边」+「钳制到 4K / 2K」（附耗时提示）
  3. 覆盖原图确认：不可逆，建议另存
- 工程分析 `MAT.big_textures` 复用同一个向导入口。

全部改动限定在 Bekkan 专属 `core/analyzer/*` + `ui/bekkan/`；仅
`ui/bekkan/__init__.py`（Mixed）加面板注册，已向当前用户说明影响范围并获同意。

## 2. 改动内容

### 2.1 `core/analyzer/fixes.py`

- 顶部加 `import os, re`。
- `_safe_basename(name)`：datablock 名清洗非法文件名字符。
- `_save_original_copy(img, dest)`：`img.copy()` 副本 + `file_format='PNG'` +
  `save_render(dest)`，finally remove 副本。**必须副本 + 显式 PNG**：`save_render` 按
  `img.file_format` 编码、不看扩展名。
- `count_big_textures()`：返回 (大于4K 张数, 大于2K 张数)，口径与 fix 一致
  （真贴图/非链接/非动态图），大于2K 是大于4K 的超集。**注意**：读未加载贴图
  `img.size` 会逐个读文件/打包块（实测约 1.4s/300 张），调用方优先用场景缓存命中。
- **场景缓存助手**：`get_downscale_report(props)`（图片总数没变才有效，否则 None）、
  `update_downscale_report(props, n4, n2)`（写入 total=len(bpy.data.images)）。
- **备份子文件夹**：pack_keep 的原图备份统一写 `<blend_dir>/贴图备份/<基名>_原图.png`，
  不再散在 .blend 旁边；`info['backup_dir']` 回报给提示。
- `fix_downscale_textures(context, max_size, mode)`：mode 显式传参（不读 scene 属性）。
  - 前置：`bpy.data.filepath` 非空（工程已保存到磁盘）。
  - 遍历 `bpy.data.images`，跳过非 `_is_real_image` / `library` 链接图 / `MOVIE`/`SEQUENCE`；
    长边 ≤max 跳过（幂等）；等比 `img.scale()` → `img.update()`（勿 `reload()`）→ `img.pack()`。
  - `pack_keep`：scale 前 `_save_original_copy` 把原图写 `<blend_dir>/<基名>_原图.png`，
    重名 `_1/_2` 递增。
  - `pack_delete`：pack 后按 `bpy.path.abspath(img.filepath)` + `refcount` 去重，
    **仅唯一引用者**才 `os.remove`。
  - 逐图 try/except 不中断；`info` 含 mode/deleted，reason 聚合前 5 条。

### 2.2 `core/analyzer/ops.py`

`ANALYZER_OT_downscale`（`analyzer.downscale_textures_visn`）为**多步向导弹窗**：
- 属性：`mode`（覆盖原图 / 备份在文件旁边，默认备份在文件旁边）、`size`（钳制到 4K/2K，
  默认 2K）、`wizard_step`（0=检测/1=保存提示/2=选项/3=覆盖确认/99=执行；
  **属性名不能以 `_` 开头**，Blender 拒绝注册 `_step`，故用 `wizard_step`）。
- `invoke`：
  - `bpy.data.filepath` 为空（从未保存到磁盘）→ 直接 `report(ERROR)` 中止，
    **不给文件夹选择**（保存文件不是脚本该处理的），只告知「请先保存 .blend 文件」。
  - 否则 `count_big_textures()` 计数；无大贴图 → INFO 中止。
  - 进 step 0 → `invoke_props_dialog`。
- step 0 检测报告：`检测到 N 张大于 4K 的贴图、M 张大于 2K 的贴图。`
- step 1 保存提示：仅当 `bpy.data.is_dirty`（标题带 `*`）才进；确认后 `wm.save_mainfile()`。
- step 2 选项：`mode`（覆盖原图/备份在文件旁边）+ `size`（钳制到 4K/2K）+
  耗时提示「转换过程可能需要几分钟，请耐心等待。」。
- step 3 覆盖确认：文案拆短成两行避免截断，并补充「建议选『备份在文件旁边』；如已覆盖，
  需要的话可自行手动链接回来。」。
- **同步计数 + 场景缓存**（回退异步 modal）：`invoke` 优先 `fixes.get_downscale_report`
  命中缓存（后台预热已填则秒出）；失效才同步 `count_big_textures()` 一次并
  `update_downscale_report`。不再有 modal/timer/BLOCKING/进度态。
- 压缩成功后 `props.downscale_total = -1` 使缓存失效（尺寸变了要重扫）。
- execute 用 `invoke_props_dialog` 链式续弹窗（execute 内再次调用并返回 RUNNING_MODAL）；
  最终执行调 `fix_downscale_textures`，`has_run` 为真时 `_rerun_analysis` 刷新列表；
  成功提示附 `info['backup_dir']`。

### 2.5 其它

- `core/analyzer/__init__.py`：`_CLASSES` 注册 `ANALYZER_OT_downscale`（常驻，独立版随包）；
  后台预热：`_warm_up_once`（load_post 后约 2s 预热一次，返回 None 自停）经
  `_refresh_downscale_cache()`（有 scene+analyzer_props 且缓存失效才 `count_big_textures` 重扫）。
  **不做后台周期性重扫**——bpy.app.timers 跑在主线程、重扫是 I/O，会在工作途中冷不丁卡住
  （用户实测担忧）；图片数变化后的重扫改由向导打开时同步触发（用户主动，可接受）。
  `bpy.app.timers` 在 5.2 不支持 `in` 成员判断，注册/注销一律 try/except 幂等。
- `ui/bekkan/__init__.py`（Mixed）：接入 `light_compose_panel` 注册/注销。
- **`props.py` 不再有 `downscale_mode`**；新增 `downscale_total/n4/n2`（IntProperty，随 .blend
  保存）作大贴图计数缓存，`total=-1` 或与当前图片总数不符即失效。
- 新增 `tools/test_downscale.py`：自带头部把 core/ 加进 sys.path（绕开 CLI 相对 import 坏点）。

## 3. 前置门槛的确定过程（重要）

用户最初要求「先检测、需把『文件自动打包』开启才能运行」。实施中发现：

1. **Blender 5.2 已移除全局「自动打包」偏好**：`preferences.filepaths` 下没有
   `use_auto_pack`，全偏好树也搜不到（只有 `experimental.no_data_block_packing`）。
2. 若按「有未打包的磁盘大贴图就拒绝」做硬门槛，会挡住 `pack_delete` 模式（删原图处理
   的就是未打包的磁盘图）。

最终定为**「工程必须已保存到磁盘」**，且按用户细化分两层：
- `bpy.data.filepath` 为空（从未保存）→ 直接报错中止，**不弹文件夹选择**；
- `bpy.data.is_dirty`（标题带 `*`，有未保存改动）→ step 1 提示「是否保存」，要求保存后才能运行。

持久化由工具自身保证——每张缩小的图强制 `img.pack()` 嵌进 .blend，不依赖任何全局开关。
删除模式的 OS 风险由 step 3「不可逆」确认 + `refcount` 共享文件保护兜底。

主流程保持同步阻塞（工作场景需要转换完成才能进行下一步，不接受异步）；预热改法接受但
要求直接改进；面板归属/命名不用管（灯光合成面板本就是未来多脚本的容器，本工具只是
第一个入口）；两份并行的开发日志要求合并为一份（即本文件，已删除旧的

### 7.1 预热改法：去掉 2 秒延迟 timer，并入 load_post 同步执行

原实现在 `load_post` 里注册一个 `first_interval=2.0` 的一次性 `bpy.app.timers`，想把
大贴图计数扫描的卡顿推到「后台」。但复审发现这个设计自相矛盾：`bpy.app.timers` 本身跑在
主线程，2 秒后触发时同样会让界面卡住——只是把「打开文件那一下」的卡顿挪到了
「打开文件后随便干点什么的时候」，时机对用户来说更随机、体感更差，还多一层
`try/except` 幂等处理的复杂度。

用户确认：「那不如直接开启的时候就做一次检查，反正刚启动也会卡一会儿，合并在一起」。
`core/analyzer/__init__.py` 删掉 `_warm_up_once()` 和 timer 注册，`_on_load(dummy)`
直接同步调用 `_refresh_downscale_cache()`，把扫描耗时并入文件加载本身已有的那次卡顿，
不再制造第二次不可预期的卡顿。`register()`/`unregister()` 里的 `load_post` handler
增删逻辑不变。**用户明确要求 GUI 实测确认实际体验**——本项只是设计层面的修正，
实测由用户在 §6 TODO 里跟进。

### 7.2 pack_delete 语义修正：从「删除」改为「原地覆盖」

复审发现一个真实的语义错配：`ANALYZER_OT_downscale` 的 UI 上 `pack_delete` 选项已经
标注为「覆盖原图」，但 `fix_downscale_textures` 的实际实现是 `os.remove(src_path)`——
直接删掉源文件，从未写回任何替代内容，跟「覆盖」字面意思不符。

用户提出的修复方向：先把缩小后的图导出到同名 temp 路径，再覆盖原图。复审后采纳，
落地为 `fixes.py` 新增 `_overwrite_source_file(img, path)`：写到 `path + ".tmp_downscale"`
临时文件，成功后 `os.replace(tmp_path, path)` 原子换入；中途失败（磁盘满/权限）只留
一个 `.tmp_downscale` 残留并重新抛出异常，原文件不会被写坏或提前消失。不用
`img.save()`——它按 `img.filepath` 写，但覆盖场景下 `filepath` 就是目标路径本身，
同名同时读写有风险；改用 `save_render(tmp_path)` 写到独立临时路径，并沿用原图
`file_format`（不强制转 PNG，覆盖要保持原编码/扩展名不变）。

配套改名：`fix_downscale_textures` 返回的 `info['deleted']` → `info['overwritten']`；
`ops.py` 的 `pack_delete` EnumProperty 描述、step 3 覆盖确认文案、执行成功提示的
「已删除 N 个磁盘源文件」→「已覆盖 N 个磁盘源文件」；`tools/test_downscale.py` 的
`test_mode_delete` 断言从「文件被删除」改为「文件仍存在且已被覆盖」
（`os.path.exists(src)` 应为真，检查 `info.get("overwritten") == 1`）。

### 7.3 顺带修复：refcount 单次遍历顺序漏洞（两阶段重写）

复审时发现原实现在**同一遍历**里边算 `refcount` 边做判断——如果两张 `Image` 共享同一个
磁盘源文件，先被遍历到的那张在 `refcount` 还没被第二张计入之前，就可能误判「我是唯一
引用者」，抢先覆盖了本该保留的共享源文件（因为第二张此时还没被处理，理应也要保留原图
直到自己处理完）。这是一个潜藏的顺序依赖 bug，用户没有主动提出，但既然要动这段代码，
一并修了。

`fix_downscale_textures` 改为两阶段：阶段一只读遍历 `bpy.data.images`，收集全部
待处理目标（`img, nw, nh, src_path`）并算出**完整**的 `refcount`；阶段二基于已完整的
`refcount` 逐张执行缩放/备份/打包/覆盖。两阶段之间没有任何提前落盘的操作，避免了
阶段一遍历顺序影响阶段二判断的问题。
