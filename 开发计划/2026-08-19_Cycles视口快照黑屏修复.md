# 2026-08-19 Cycles 渲染视口拍摄快照——记录成功但对比覆盖层全黑

## 目标

用户反馈：视口着色切到「渲染」（Rendered）+ Cycles 时，点「拍摄快照」右上角有
成功提示、快照列表也确实新增了一条记录，但对比覆盖层显示出来是全黑的。此前用
EEVEE/材质预览/线框/实体等其它模式都正常，问题只在 Cycles 渲染视口下出现，且
拍摄之前这个视口本身已经在正常渲染（画面已收敛，不是还在转圈采样）。

## 根因

`core/snapshot.py::_capture_offscreen()` 靠 `GPUOffScreen.draw_view3d(..., 
do_color_management=True)` 做"离屏重新画一次当前视口"来拿画面。这条路径对
EEVEE/EEVEE Next/Workbench 是同步栅格化——一次调用就能拿到完全收敛的结果，文件
头部注释也明确写了这个假设（"EEVEE 无采样竞态，比旧延时截图更可靠"）。

Cycles 是渐进采样引擎：交互视口里那份看起来已经收敛好的画面，是原生视口 session
经过多帧累积采样才画出来的。`off.draw_view3d()` 传的虽然是同一个 `space`/
`region`，但它是在一块全新的离屏帧缓冲上重新触发一次渲染调用——对 Cycles 来说这
相当于开了一个全新的、零采样的 session，一次同步调用根本来不及攒够采样，读出来
的自然是黑图（或半成品），跟眼前视口里那份早就收敛好的画面是两份完全不同的渲染
结果。这不是本项目引入的 bug，是"离屏重渲染"这个手段本身对渐进采样引擎不成立。

## 方案：Cycles 等引擎改成异步读「已经画好的真实帧缓冲」，不重新触发渲染

不再对 Cycles 尝试离屏重渲，而是换一种完全不依赖引擎类型的思路：**直接读当前
视口已经画在屏幕上的那一帧**——用户眼睛看到的就是想要拍的东西，没有必要重新渲染
一份。具体做法：

1. 摘掉本窗口当前的对比覆盖层显示标记（跟原来的同步路径一样，避免自己拍到自己）。
2. 在该视口的 `SpaceView3D` 上挂一个**一次性** `WINDOW`/`POST_PIXEL` 绘制句柄，
   强制 `tag_redraw()` 排一次真实重绘。
3. 这个一次性句柄在真正被调用时（也就是下一次视口真实重绘、3D 内容和所有正常
   覆盖层都已经画完之后），用 `gpu.state.active_framebuffer_get().read_color(...)`
   读当前已经绑定好的真实帧缓冲，把像素原样存进模块级的 `_pending_capture[area_id]`
   ——**不碰任何 RNA/bpy.data**，只是读像素存进纯 Python 字典。
4. 拍摄发起方是一个 modal 操作符（用极短间隔的 timer 轮询 `_pending_capture`），
   等这份数据出现后，在操作符自己的、安全的上下文里把像素数据封成 `GPUTexture`
   并调用现有的 `_finish_capture()`（写 `scene.snapshot_list` 等 RNA 数据）。

第 3 步特意不在绘制回调内部自己调用 `draw_handler_remove` 摘掉自己——在绘制回调
执行期间移除自身句柄有失效风险，统一交给 modal 操作符在成功/失败/超时三条路径
里做，绘制回调本身只用「`area_id` 已经在 `_pending_capture` 里就直接跳过」防止
消费前被重复读。

### 顺带简化：这条路径不需要再手动补摄像机遮罩

原来的离屏路径需要手动算一次摄像机遮罩（Passepartout）矩形再压黑，是因为
`draw_view3d` 离屏重渲不会带出"摄像机遮罩"这个交互视口专属画的 2D 引导层
（见 `_passepartout_mask` 的注释）。异步路径读的是**真实**帧缓冲，摄像机遮罩本来
就是 Blender 正常绘制流程画出来的一部分，读的时候已经天然包含在里面了——不需要
再手动应用一次遮罩（如果手动再补一次会变成遮罩区域被压黑两遍，比原图更黑）。

### 判断走哪条路径

`_SYNC_ENGINES = {"BLENDER_EEVEE", "BLENDER_EEVEE_NEXT", "BLENDER_WORKBENCH"}`，
`TakeSnap.invoke()` 检查 `scene.render.engine` 是否在这个集合里：在，走原来的
`execute()` 同步离屏路径；不在（Cycles，以及任何走 `RenderEngine` API 接的第三方
渐进采样渲染器插件），走新的异步读帧路径。选"排除法"（不在已知安全集合里的都走
异步）而不是"只认 Cycles"，是因为任何渐进采样的第三方渲染引擎插件理论上都有同样
的问题，异步路径对所有引擎都成立（本质是"读屏幕上已经画好的东西"，不依赖引擎
具体实现），没有必要只narrow修 Cycles 这一个。

## 改动（`core/snapshot.py`，Mixed 共同维护文件）

跨边界说明：改动集中在 `TakeSnap` 这一个操作符类（从纯 `execute` 改成
`execute`+`invoke`+`modal` 三段，`execute` 保留给同步引擎，新增 `invoke`/`modal`
走异步路径）+ 几个新增的模块级异步读帧辅助函数（`_ensure_async_handler`/
`_rm_async_handler`/`_read_backbuffer`）+ `_reset_on_load`/`unregister` 里补上
对新增模块级字典的清理。`object.take_snapshot` 这个 idname、UI 按钮、快捷键
（Ctrl+Alt+右键）都没变，两个模式都是通过按钮/快捷键触发（走 `INVOKE_DEFAULT`
上下文），不存在依赖"调用后立刻同步拿到结果"的脚本化用法，所以从
纯 `execute()` 换成 `invoke()`+`modal()` 对现有调用方是透明的。已确认没有其它
地方（包括回归测试脚本）以 `EXEC_DEFAULT` 方式调用这个操作符。需要更新
`开发计划/模块归属标注.md`——不需要（改动范围仍在原来记录的 snapshot 快照
模块内，没有新增跨模块耦合）。

## GUI 实测踩坑：`GPUFrameBuffer.read_color()` 真实签名

没有 Blender 环境实测直接写代码，第一版猜错了 `read_color()` 的参数：

1. 第一次猜的是 `read_color(x, y, xsize, ysize, channels, slot, format, data)`
   （8 个位置参数，参照某些旧版/其它 GPU API 文档里常见的「多一个 slot」写法），
   实测报错 `takes exactly 7 positional arguments (8 given)`。
2. 去掉 `slot`，改成 `read_color(x, y, xsize, ysize, channels, format, data)`
   （7 个参数，猜测第 6 位是格式字符串 `"FLOAT"`），实测报错
   `'str' object cannot be interpreted as an integer`——说明第 6 位根本不是格式
   字符串，而是要求 int 的参数。
3. 猜第 6 位是 `slot`（int，颜色附件槽位）、第 7 位继续传自己构造的 `Buffer`
   对象（`fb.read_color(0, 0, w, h, 4, 0, buf)`），实测报错
   `expected a string, got Buffer`——说明第 7 位也猜错了，它要的是字符串。
4. 真实签名（Blender 5.2）：`read_color(x, y, xsize, ysize, channels, slot, format) -> Buffer`
   ——**这个方法不接受外部传入的缓冲区去写，而是自己创建并 return 一个新
   `Buffer`**。第 6 位 `slot` 是帧缓冲颜色附件槽位（int，固定传 `0`），第 7 位
   `format` 才是格式字符串。改成
   `buf = fb.read_color(0, 0, w, h, 4, 0, "FLOAT")`，不再预先构造
   `gpu.types.Buffer(...)`，用返回值即可。签名本身此时已经对，但传的格式字符串
   还是错的——见下一条。
5. 签名对了之后能拍出东西了，但先是「拍成功、叠加层整块透明看穿到真实场景」，
   强制 alpha=1 之后变成「整块纯黑」，两次症状连起来暴露了同一个更深的错误：
   **格式参数传的是 `"FLOAT"`，但真实窗口后台缓冲实际是 8-bit（`UBYTE`）**，
   离屏路径用的是显式 `RGBA32F` 离屏缓冲，两者格式不一致——按 `FLOAT` 去读一块
   实际是 `UBYTE` 的缓冲，等于把 8-bit 数据错当 32-bit 浮点位模式解释，数值几乎
   全部退化成接近 0 的垂圾数（表现为纯黑），alpha 通道同理不可信（表现为全透明）。
   改成按真实格式 `"UBYTE"` 读，构造 `gpu.types.Buffer("UBYTE", ...)`，直接匹配
   `GPUTexture(format="RGBA8", ...)`，不需要经过浮点量化这一步；alpha 依旧手动
   强制成 255（真实后台缓冲的 alpha 通道本身没有意义，跟格式对不对无关，两条路径
   都需要这一步）。
6. 按 `"UBYTE"` 读对之后，`GPUTexture(...)` 构造函数本身又报
   `GPUTexture.__new__: Only Buffer of format `FLOAT` is currently supported`——
   `GPUTexture(data=...)` 目前只认 `FLOAT` 格式的 `Buffer`，`UBYTE` 直接喂会被拒
   （跟"真实缓冲是 UBYTE"这件事没有冲突，是两个不同层面的格式要求：读的时候要
   按真实格式读对，喂给 `GPUTexture` 的时候又必须是 `FLOAT`）。修正为：按
   `"UBYTE"` 读出真实数据后，转成 `float32` 并归一化到 `[0,1]`（`/255.0`），
   alpha 通道强制设成 `1.0`，再包一层 `gpu.types.Buffer("FLOAT", ...)` 喂给
   `GPUTexture`——跟离屏路径「`RGBA32F` 离屏 → `FLOAT` Buffer → `GPUTexture`
   内部量化」殊途同归，只是这里多了一步"先按真实格式读对，再转换成 FLOAT"。

## 追加：异步读帧方案本身不成立，实测始终是黑图——根因是读错了帧缓冲

按上面 1-6 的签名/格式修正全部落地、GUI 实测后，异步路径依然**始终拍出纯黑**：
alpha 强制置 1、格式改成真实的 `UBYTE` 再转 `FLOAT` 喂给 `GPUTexture` 之后，黑图
症状没有变化——这**反证**了"格式误读"是根因（如果只是格式误读，改成正确格式后
应该能看到花屏或至少部分正确的内容，而不是纹丝不动的纯黑）。

为定位真正原因，让用户在同一个视口下跑了一个独立诊断：直接调用 Blender 自带的
`bpy.ops.screen.screenshot_area(filepath=...)`（跟本方案的手动 `read_color()`
毫无关系的另一条路径），结果**截图内容完全正常，看得到真实的 Cycles 渲染画面**。
这证明真实像素在窗口/编辑器层面是可以正常访问到的，问题精确定位在：**我们在
`POST_PIXEL` 绘制回调里用 `gpu.state.active_framebuffer_get()` 拿到的那个帧缓冲，
根本不是 Cycles 最终合成结果写入的目标**——Cycles 的渐进采样视口渲染疑似走了一条
和 EEVEE/Workbench 标准视口 FBO 不同的 GPU 合成路径，我们的绘制回调看不到它（这也
解释了为什么 EEVEE/Workbench 从一开始就没出过这个问题——它们确实用的是标准路径，
我们的回调看得到）。

### 方案调整：弃用手动 read_color()，改用 screen.screenshot_area()

既然 `screenshot_area()` 已经实测证实能看到 Cycles 真实画面，直接换成它，不再猜测
`read_color()` 的更多参数排列组合：

1. `screenshot_area(filepath=...)` 把整个 area（含标题栏/工具栏/N 面板，不只是
   3D 视口内容）截图存成临时 PNG 文件。
2. `bpy.data.images.load()` 读回，`colorspace_settings.name` 设成 `Non-Color`/
   `Raw`，跳过 sRGB 解码（截图字节本身就是最终显示编码值，画回前统一交给 shader
   预解码，语义要跟 `_capture_offscreen` 对齐）。
3. 用 `region.x/y` 相对 `area.x/y` 的像素偏移，把截图裁剪到只剩 3D 视口那部分
   （`region` 范围），丢掉标题栏/工具栏/N 面板；额外按截图实际像素数与 area 逻辑
   尺寸的比例算一个缩放系数，兜底 HiDPI/系统缩放下两者不是 1:1 的情况（缩放为 1
   时等价于直接用像素偏移，不做任何变换）。
4. 裁剪后 alpha 强制置 1（跟真实后台缓冲同理，PNG 的 alpha 未必有意义），转成
   `FLOAT` `Buffer` 喂 `GPUTexture(format="RGBA8", ...)`。
5. 清理临时 `Image` 数据块和临时文件。

`screenshot_area()` 本身是同步阻塞调用（不需要等下一次真实重绘），这让整个方案
**回归成纯 `execute()`**——原来为了配合异步读帧新增的 `invoke()`/`modal()`/定时器/
一次性 `POST_PIXEL` 句柄全部撤掉，`_ensure_async_handler`/`_rm_async_handler`/
`_read_backbuffer`/`_async_hdl`/`_pending_capture` 全部删除，`TakeSnap` 恢复成
和最初版本一样"引擎判断 -> 走对应捕获函数 -> `_finish_capture`"的单一 `execute()`
结构，只是同步分支从"离屏重渲"变成"离屏重渲 or 截图"两选一——比引入 modal 状态机
更简单也更不容易出边界情况的 bug。

摄像机遮罩（Passepartout）：跟异步方案原来的判断一致——截图读的是真实已经画完
的那一帧，遮罩本来就是正常绘制流程画出来的一部分，不需要再手动补一次。

跨边界说明：改动仍然全部在 `core/snapshot.py`（Mixed 文件）内，`TakeSnap` 这个
操作符类、公开 idname、UI 按钮、快捷键都没有变化，属于同一个已获批准的修复范围内
的实现调整（从"异步读帧缓冲"换成"截图裁剪"，目标仍是"读当前视口已经画好的真实
一帧，不重新渲染"），不需要更新 `模块归属标注.md`。

## 已知限制 / 待验证

- 区域到视口的裁剪偏移量算法（`region.x/y - area.x/y`，乘以截图像素数与 area
  逻辑尺寸的缩放比）没有在真实 Blender 环境里验证过——尤其是 HiDPI/系统缩放场景
  下缩放系数是否真的等于 `1.0`，或者 Blender 是否已经在 `area.width`/`region.width`
  里把缩放折算进去了，这一步存在裁剪偏移小幅误差的风险（如果发现快照内容整体
  偏移了几像素、或者边缘被切掉一条，需要反馈具体现象以便调整偏移公式）。
- Non-Color/Raw 色彩空间标记假设截图 PNG 字节即最终显示编码值，跟 `_capture_offscreen`
  的存储语义对齐——需要用户对比同一份场景在 EEVEE 下的快照效果，确认 Cycles
  快照颜色不发暗/不发灰（如果画面整体偏暗，大概率是这里的色彩空间假设或
  `_DRAW_DECODE_SRGB` 预解码环节有一层没对齐）。
- 摄像机遮罩（Passepartout）在截图路径下确认只压黑一次，不重复、不缺失。
- EEVEE/EEVEE Next/Workbench 路径完全没动，需要确认没有回归。
- 临时文件/临时 `Image` 数据块的清理路径（`finally` 块）需要确认多次连续拍摄
  不会在磁盘或 `bpy.data.images` 里遗留垃圾。

## 追加：已开着对比覆盖层时再拍一张，把旧覆盖层也拍了进去

用户实测反馈：上面的截图路径本身没问题，画面正常、颜色正常、裁剪正常、遮罩正常，
但发现一个新 bug——如果这个窗口当前正在显示对比覆盖层（`disp_snap[area_id]` 已经
指向某张旧快照），这时候再拍一张新的，新快照里会把屏幕上那张旧的对比覆盖层也一起
拍进去，而不是先隐藏旧覆盖层再拍摄纯净的实景。

### 根因：`disp_snap.pop()` 只清空了一个 Python 字典，没有让这一刻的屏幕真的重绘

`TakeSnap.execute()` 在调用捕获函数之前确实执行了 `disp_snap.pop(area_id, None)`
摘掉显示标记——但 `screenshot_area()` 读的是"此刻已经在屏幕上的像素"，不会主动
触发一次新的重绘。摘掉标记这个动作本身不会让 Blender 立刻重新执行一遍
`SpaceView3D` 的 `WINDOW`/`POST_PIXEL` 绘制回调（`_draw`）——如果窗口在这一瞬间
碰巧没有发生任何重绘，屏幕上实际显示的仍然是摘掉标记*之前*的最后一帧画面，也就是
带着旧对比覆盖层的那一帧，`screenshot_area()` 原样把它截了下来。

这跟"读错了帧缓冲"（Cycles 黑图问题）是两个完全不同层面的 bug：黑图问题是读的
目标本身不对；这次是读的目标本身没问题，但读的时机太早——早于"用新状态重绘"这一步。
离屏路径（`_capture_offscreen`）完全不受影响，因为它是在一块独立的离屏缓冲上
重新触发一次 `draw_view3d`，从来不会经过、也不会触发真实窗口的 `POST_PIXEL`
绘制回调，所以离屏路径原本就看不到 `disp_snap` 有没有被摘掉这件事。

### 修复：截图前先强制走一次同步重绘+swap

在 `_capture_screenshot()` 里，调用 `screenshot_area()` 之前先调用：

```python
bpy.ops.wm.redraw_timer(type='DRAW_WIN_SWAP', iterations=1)
```

这个操作符会同步触发一次真正的窗口重绘并等待 swap 完成——此时 `disp_snap` 已经
在 `execute()` 里被摘掉了，`_draw()` 回调会因为 `disp_snap.get(area_id)` 查不到
键而直接跳过绘制，重绘出来的这一帧是干净的实景，`screenshot_area()` 紧接着读到
的就是这一帧，不会再把旧覆盖层拍进去。

跨边界说明：改动仍然只在 `core/snapshot.py::_capture_screenshot()` 内新增一行，
不涉及其它文件，属于上面已获批准的截图方案的必要补丁（没有这一行，截图方案在
"覆盖层已开启时再拍摄"这个具体场景下就是错的），不需要更新 `模块归属标注.md`。

### 已知限制 / 待验证

- `redraw_timer(type='DRAW_WIN_SWAP')` 是否在所有 GPU 驱动/多窗口环境下都能保证
  "调用返回时重绘已经真正完成"没有 100% 把握，需要用户确认修复后连续多次拍摄
  （尤其是"开着对比、立刻再拍"这个操作节奏）不再出现旧覆盖层混入新快照的情况。
- 这行修复只加在截图路径（`_capture_screenshot`），离屏路径不需要、也没有加，
  需要确认 EEVEE/Workbench 下开着对比覆盖层再拍摄依旧正常（预期本来就没问题，
  这次没有改动这条路径）。

## 测试结果（追加）

`python -m compileall -q .` 全量无报错。GUI 实测（开着对比覆盖层时连续拍摄多张，
Cycles 场景为主，EEVEE 场景做一次回归确认）留给用户在 Blender 里验证。

## 追加二：`DRAW_WIN_SWAP` 把 Cycles 拍成了纯灰——重绘 API 选得太重

上一条修复用户实测后反馈**完全变成灰色**（连黑图都不是），且没有任何报错。分析
判断：`bpy.ops.wm.redraw_timer(type='DRAW_WIN_SWAP', ...)` 是窗口级别的强制重绘，
语义上比"让这个视口的 2D 覆盖层按最新状态重新画一遍"重得多——它很可能把 Cycles
视口的渐进采样 session 当成"发生了一次会话级别的变化"而重新起播，这跟最初
"离屏重渲 = 全新 Cycles session = 零采样黑图"是同一类陷阱，只是这次表现成灰色
（Cycles 刚起播、还没有第一批采样时的占位色，比全黑更早一个阶段）。

`redraw_timer` 本质是 Blender 内部做性能基准测试用的调试 API，`DRAW_WIN_SWAP`
这个档位在文档语境里就是"重复完整重绘整个窗口 N 次、用来测帧率"，不是给插件当
"轻量触发一次重绘"来用的——选它是把这个 API 想得太轻量了。

### 修复：换成范围更小的 `DRAW_SWAP`（限定在 temp_override 的 region）

改为 `bpy.ops.wm.redraw_timer(type='DRAW_SWAP', iterations=1)`，且保持在
`context.temp_override(area=area, region=region)` 的范围内调用，理论上把重绘
范围收窄到当前 region，不去碰其它区域或触发场景级别的重新求值。**这一步未经
实机验证**——如果这次还是出现异常（灰屏/重新起播/明显变慢/其它花屏现象），说明
"用 redraw_timer 强制重绘再截图"这个思路本身对 Cycles 不安全，需要放弃，改成
其它排队等待方式（比如等一次自然的 `tag_redraw` 而非主动强制重绘，或者接受
"截图前先切一次纯 2D 覆盖层的局部重绘"根本做不到、转而在覆盖层绘制端做防御——
比如 `_draw()` 在被临时挂起的一个标记下自行跳过绘制，而不是指望外部重绘）。

跨边界说明：改动仍然只在 `_capture_screenshot()` 内，只改了 `redraw_timer` 的
`type` 参数值，不涉及其它文件，不需要更新 `模块归属标注.md`。

## 追加三：EEVEE/EEVEE Next/Workbench 也统一改用截图路径

用户反馈 EEVEE 拍摄快照现在是"离屏重新渲染一次"（`_capture_offscreen`，从项目
最早版本就存在的逻辑，这次之前没有改过），这条路径有两个实际问题：会等待重新
收敛才返回（不是"立即截取当前屏幕"，大场景/高采样下有明显延迟），且离屏重渲
是在独立缓冲上重新触发一次渲染调用，理论上跟屏幕当前实际显示的那一帧可能存在
细微出入（不是眼见为实）。经用户确认（"换成截图路径"），统一改成所有引擎都走
`_capture_screenshot()`，不再区分 `_SYNC_ENGINES`：

- 删除 `_SYNC_ENGINES` 常量、`_capture_offscreen()`、`_passepartout_mask()`
  （摄像机遮罩本来就是正常绘制流程画出来的一部分，截图路径天然带着，不需要再
  手动算矩形补一次）、`_capture_offscreen` 专用的 `location_3d_to_region_2d`
  导入。
- `TakeSnap.execute()` 不再按 `scene.render.engine` 分支，统一调用
  `_capture_screenshot(context, area, region)`；不再需要 `space`/`space.region_3d`，
  相应的取值和校验一并简化掉。

跨边界说明：这是对已获批准的"截图路径"范围的扩大——从"仅 Cycles 等非同步引擎"
扩大到"所有引擎统一"，`core/snapshot.py` 是 Mixed 文件，此次改动经当前用户明确
选择确认（"换成截图路径（推荐）"），不需要更新 `模块归属标注.md`（改动范围仍在
原有记录的 snapshot 模块内）。

### 已知限制 / 待验证

- `DRAW_SWAP` 是否能在 EEVEE/Workbench 下依然安全触发重绘（预期比 Cycles 更没有
  副作用风险，因为这些引擎本来就是同步栅格化，没有"渐进采样会话"这个概念）。
- EEVEE 下改成截图路径后，需要确认画面颜色/清晰度跟原来的离屏路径版本没有肉眼
  可见差异（截图路径经过一次 PNG 编解码，理论上无损，但没有实测对比过）。
- 大场景/高分辨率窗口下截图路径的耗时是否比离屏路径更快——这是用户提出这个需求
  的初衷之一（"及时截取对比，而不是等待完整图像载入"），需要实测确认确实变快了。

## 追加四：`DRAW_SWAP` 依然把 Cycles / EEVEE Next 拍成灰色——`redraw_timer` 这条路整体放弃

用户实测反馈：降级到 `DRAW_SWAP` 之后，Cycles 依旧是灰色；而且这次连 EEVEE Next
也变成了灰色（此前从没出现过，说明问题不是"选错了哪个 redraw_timer 档位"，是
`_capture_screenshot()` 里**无条件**在每次截图前都调一次 `redraw_timer` 这件事
本身——不管传哪个 `type`，只要强制走一次 `redraw_timer`，就会让 Cycles 和
EEVEE Next 这类带渐进累积/时序累积（temporal accumulation）的引擎把这次重绘当成
"场景变了"，从零重新起播，截图截到的是几乎没有采样的占位帧（灰色）。这跟最早
"离屏重渲=全新 session=黑图"是同一类陷阱的另一种表现形式，只是这次连"轻量"
的区域级 `DRAW_SWAP` 都没能避开。

另外定位到一个此前没意识到的问题：`redraw_timer` 调用被放在了 `_capture_screenshot()`
内部、无条件执行——也就是说，**哪怕根本没有旧覆盖层需要摘掉**（第一次拍摄、或者
当前没有开对比），每次拍摄也都会强制走一次这个有破坏性的重绘，这解释了为什么这次
反馈里连基础拍摄（非"重新拍摄覆盖已有对比"的场景）也受到影响。

### 修复：完全放弃 `wm.redraw_timer`，改用 `tag_redraw()` + modal 定时器等一次自然重绘

`redraw_timer` 是给性能测试写的调试 API，语义上是"强制走一次完整的场景求值 +
渲染"，跟平时鼠标划过视口、切换窗口焦点等操作触发的"正常重绘"完全不是一回事——
后者不会让 Cycles/EEVEE Next 重新起播（不然日常使用早就没法用了）。据此改成：

- `_capture_screenshot()` 里删掉 `redraw_timer` 调用，只负责截图，不管重绘。
- `TakeSnap` 拆成两条路径：
  - **没有旧覆盖层要摘**（`prev is None`，包含"第一次拍摄"和"当前没开对比"）：
    维持原来的"立即截图"，不引入任何等待，跟用户最初确认"可以拍摄，都 ok"
    时的行为完全一致。
  - **有旧覆盖层要摘**：`disp_snap.pop()` 之后调 `area.tag_redraw()` 打一个
    重绘标记，然后用 `wm.event_timer_add(0.05, ...)` + `modal_handler_add()`
    把截图动作推迟到下一个 TIMER 事件里执行——让 Blender 走一次它自己正常的
    事件循环重绘（跟移动窗口/切焦点触发的重绘性质相同），再截图。全程没有调用
    任何"强制刷新"的调试 API。

跨边界说明：改动仍然只在 `core/snapshot.py` 内，只涉及 `_capture_screenshot()`
和 `TakeSnap`，不影响其它文件；`_classes` 列表、idname、快捷键绑定都没变
（`TakeSnap` 通过 `bl_idname`/快捷键触发的调用方式不变，`execute()` 允许返回
`RUNNING_MODAL` 是 Blender Operator 的标准用法，键盘快捷键和菜单调用都兼容）。
不需要更新 `模块归属标注.md`。

### 已知限制 / 待验证（这是目前最没底的一次改动，务必重点验证）

- **0.05 秒后的第一个 TIMER 事件，是否一定意味着 Blender 已经真正完成了一次
  重绘并把新帧提交到屏幕**——没有 100% 把握，这是基于"Blender 主循环通常会在
  分发事件前处理完所有待重绘区域"的一般性认知，没有查到官方文档明确保证这个
  时序。如果这次实测发现"有时候还是会拍到旧覆盖层"（概率性复现，不是每次都
  出问题），说明这个等待时机不够可靠，需要改成等多个 TIMER 节拍、或者换成
  别的同步机制。
- 如果这次 Cycles/EEVEE Next 还是灰色/黑色，说明"摘覆盖层后需要强制看到新一帧"
  这个需求本身，在不触发 `redraw_timer` 类重绘的前提下可能根本做不到可靠等待，
  需要放弃"等重绘"的思路，改成完全不同的方案（比如让 `_draw()` 自己感知到
  "本帧应该跳过覆盖层绘制"的一次性标记，在被摘除的**下一次自然重绘**时生效，
  而截图操作不再主动等待，只是纯粹依赖用户下一次正常交互——但这样"立即拍摄"
  的体验会打折扣，需要跟用户重新讨论取舍）。
- EEVEE Next 变灰色是新证据，还没有单独验证过是不是所有 EEVEE Next 场景都会
  这样，还是只有开了某些效果（屏幕空间反射/GI、软阴影等依赖时序累积的功能）
  才会——如果这次 modal 方案验证通过，这条信息就不再重要；如果还失败，需要
  用户提供更多细节（是否开了这些效果）帮助进一步定位。
