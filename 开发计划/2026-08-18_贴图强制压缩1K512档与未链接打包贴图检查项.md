# 2026-08-18 贴图强制压缩新增 1K/512 档 + 新检查项「已打包未链接贴图」+ 操作难易排序修复

## 目标

用户反馈两个工程分析相关的小 bug/需求：

1. 贴图强制压缩向导只有 4K/2K 两档，需要补上 1K 和 512；顺带提到工程里有几张 4K
   贴图没被检测到，怀疑跟 Shader Editor 里"导入了但没链接"的贴图有关；并明确提出
   一个新检查项需求：已导入并自动打包、但在材质节点里没真正链接使用的贴图，应该
   提示是否清除以减小工程体积。
2. 「操作难易」排序方向反了——应该易到难（最容易操作的在最上面），实际显示是反的。

## 改动一：4K 贴图检测漏检 + 新检查项「已打包未链接贴图」

### 根因：`check_big_textures` 用面积判定，跟 `count_big_textures` 的长边判定口径不一致

`core/analyzer/checks.py::check_big_textures()` 原来用 `w*h >= 4096*4096`（总像素
面积达到一整个 4096² 正方形）判定"是不是 4K"，但常见的非正方形"4K"贴图（比如
4096×2048 的贴图条、HDRI）面积远小于 1670 万像素，永远不会被这个阈值命中——这正是
用户说"工程里有几张 4K 贴图却没检测到"的根因，跟 Shader Editor 链接与否无关。
`core/analyzer/fixes.py::count_big_textures()`（供强制压缩向导用）一直用的是长边
`max(img.size) > 4096`，两个函数口径不一致。改为 `check_big_textures` 也用长边
`max(w, h) >= 4096`，跟 `count_big_textures` 对齐。

### 新检查项：`MAT.unlinked_packed_images`（`checks.py::check_unlinked_packed_images`）

用户提到的"导入但没链接"现象本身是真实存在的、值得单独做成检查项的问题（跟上面
的漏检是两件独立的事）。新检查项只看 `img.packed_file` 存在（真正占 `.blend`
体积的）的贴图，抓两种情况：

1. 材质/世界节点树里有 `TEX_IMAGE` 节点引用了这张图，但节点输出一个都没接出去。
2. 压根没被任何材质/世界节点树引用（但 `users > 0`，不是真孤儿）。

真孤儿（`users == 0`）已经由现有 `check_orphan_data` / `DATA.orphans` 覆盖，这里
故意不重复统计，只抓"有引用但引用是摆设"这个之前没人管的缝。范围限制：只扫材质和
世界节点树，合成器/几何节点里的贴图引用不在这次检测范围内（已知限制）。

配套修复 `fixes.py::fix_remove_unlinked_packed_images`：直接用检测时记在
`item.obj_names` 里的名字删除对应 `Image` 数据块（不重新扫描判断，避免检测和修复
之间节点连线又变了导致的不一致），已在 `ops.py::ANALYZER_OT_fix.execute()` 里挂上
`MAT.unlinked_packed_images` 分支。

### 强制压缩向导新增 1K / 512 档

`ops.py::ANALYZER_OT_downscale`：
- `size` EnumProperty 补上 `'1024'`/`'512'` 两个选项。
- `count_big_textures`/`get_downscale_report`/`update_downscale_report` 从
  `(n4, n2)` 二元组改成 `(n4, n2, n1, n512)` 四元组，向导第一步的提示文案同步显示
  四档统计。改动跨了 `fixes.py`（口径与缓存函数）、`props.py`（新增
  `downscale_n1`/`downscale_n512` 两个场景缓存字段）、`__init__.py`（
  `_refresh_downscale_cache` 解包/写入四元组）、`ops.py`（向导 `invoke`/`draw`）。
- `fix_downscale_textures(context, max_size, mode)` 本身对目标尺寸是通用的
  （只是长边钳制上限），512/1024 不需要改这个函数。

### 已更新的回归测试

`tools/test_downscale.py::test_count`/`test_cache` 原本按 `(n4, n2)` 二元组断言，
同步改成 `(n4, n2, n1, n512)` 四元组（`3072`/`4096`/`8192` 三张测试图现在都要落在
`>512`/`>1024`/`>2048` 里，只有 `8192` 落在 `>4096`）。

## 改动二：「操作难易」排序方向反了——UIList `filter_items` 返回的是错误的排列

### 根因：`flt_neworder` 语义搞反了

`ui/bekkan/analyzer_panel.py::ANALYZER_UL_finding.filter_items()` 原来的实现：

```python
order = sorted(range(n), key=_key)
return [self.bitflag_filter_item] * n, order
```

`_EASE_RANK`/`_IMPACT_RANK` 的取值本身是对的（一键在前、严重在前，都是升序），问题
在 Blender `UIList.filter_items` 的 API 契约上：`flt_neworder` 要求的是
**"原索引 → 新显示位置"的反向映射**（`neworder[原索引] = 新位置`），而不是"排好序
后的索引列表"本身（`order[k] = 第 k 小的那一项的原索引`）——这两者不是同一个数组，
直接把 `order` 当 `neworder` 传回去，会让实际显示顺序整体错位（手算过一个 4 项的
例子，得到的是跟预期完全相反的顺序），这才是用户反馈"难易排序方向反了"的真正根因，
跟 rank 常量的取值方向是两件独立的事。

### 修复

在返回前显式构造反向排列：

```python
order = sorted(range(n), key=_key)
neworder = [0] * n
for new_pos, orig_idx in enumerate(order):
    neworder[orig_idx] = new_pos
return [self.bitflag_filter_item] * n, neworder
```

## 归属说明

本次改动全部落在 Bekkan 专属模块（`core/analyzer/`、`ui/bekkan/analyzer_panel.py`、
`tools/test_downscale.py`），不涉及 Pond 专属或 Mixed 共同维护文件，不需要更新
`模块归属标注.md`。

## 测试结果

`python -m compileall -q .` 全量无报错。GUI 实测清单（无 Blender 环境，留给用户）：

- 强制压缩向导第一步能看到 4K/2K/1K/512 四档统计数字，选 1K 或 512 能正常压缩。
- 工程分析简单检查能跑出 `check_big_textures` 长边判定后的结果——之前漏检的非
  正方形 4K 贴图（比如 4096×2048）现在应该出现在"大贴图"检查项里。
- 找一个 Shader Editor 里有贴图节点、但节点输出没连接任何地方的材质（或者删掉
  节点连线后仍保留已打包贴图的场景），跑一次分析，确认能看到新检查项「已打包但未
  在材质中链接使用的贴图」，点"快速修复"确认能正确删除、不报错、且不误删仍在用的
  贴图。
- 工程分析结果列表切到「操作难易」排序，确认最上面是"一键"难度、最下面是"较难"
  （之前是反过来的），「不再提醒」的条目始终沉底不受影响；切回「影响程度」排序
  确认没有被这次改动带偏。
