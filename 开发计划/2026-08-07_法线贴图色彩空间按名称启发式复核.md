# 2026-08-07 法线贴图色彩空间检测：按名称启发式复核兜底

## 目标

用户反馈 `MAT.normal_map_colorspace` 的精确检测（要求贴图必须直连在「法线贴图」
NORMAL_MAP 节点的 Color 输入上）漏检复杂节点图——具体案例：把法线贴图跟材质里
Geometry 节点的 Normal 输出混合后，直接接到一个节点组内部 Diffuse BSDF 的 Normal
输入上，全程没有经过任何 NORMAL_MAP 节点。讨论后确认：这种「无锚点节点」的连接方式
理论上只能靠通用图遍历（顺着任意节点找到某个叫 Normal 的插槽）才能结构化检测，
成本较高且仍非 100% 覆盖；用户拍板先上按贴图名称的启发式兜底，方案：

1. 保留现有精确检测（NORMAL_MAP 直连）不变。
2. 在精确修复跑完之后，额外扫一遍已经用在材质节点树里、名字像法线贴图
   （包含 normal/nrm/norm/法线）、但没被精确检测抓到的贴图，弹窗追问是否也一并
   改成 Non-Color——因为不是所有叫 normal 的贴图都必须用 Non-Color，这批只提示
   不强制自动改。

## 改动

### 1. `core/analyzer/fixes.py`：新增三个函数

- `_looks_like_normal_name(name)`：名称小写后包含 `normal`/`nrm`/`norm`/`法线`
  任一关键字即命中。
- `_images_wired_into_normal_map_node()`：只读版的精确检测遍历（跟
  `fix_normal_map_colorspace` 同一套「顶层节点树 → NORMAL_MAP 节点 → Color
  输入直连的 TEX_IMAGE」逻辑），返回已被精确检测覆盖的贴图名集合，供下面的函数
  排除重复提示。
- `find_normal_named_review_images(context)`：扫材质顶层节点树里所有 TEX_IMAGE
  节点，排除已被精确检测覆盖、已经是 Non-Color、名字不含法线关键字的贴图，
  剩下的按名称排序返回——是「需要用户确认」的候选名单，不代表一定该改。
- `set_images_colorspace_noncolor(image_names)`：批量把指定名称的贴图设成
  Non-Color，供确认后应用。

范围限制：跟精确检测一样只扫材质顶层 `node_tree.nodes`，不递归进节点组内部——
如果 TEX_IMAGE 节点本身藏在节点组里，这一版的启发式扫描也扫不到（用户描述的
案例里贴图本身在顶层，只是混合后的结果流进了节点组，所以能被这版扫到）。

### 2. `core/analyzer/ops.py`：两个入口都接上二次确认弹窗

- 顶部 import 加 `BoolProperty`。
- **`ANALYZER_OT_fix`**（工程分析「快速修复」入口，按 `key` 分发多种修复类型）：
  新增 `also_fix_review` BoolProperty、`_review_candidates` 实例属性、
  `invoke()`、`draw()`。`invoke()` 只在 `self.key == "MAT.normal_map_colorspace"`
  且扫到候选贴图时才弹 `invoke_props_dialog`，其余分支/无候选时直接调用
  `self.execute(context)`，等价于原来没有 `invoke()` 时「点击即执行」的行为，
  不影响其它 27 个检查项的修复按钮。`draw()` 同样只在这个 key 且有候选时画内容，
  其余情况直接 `return`（重做面板留空，不会给别的修复类型显示无关 UI）。
  `execute()` 的 `MAT.normal_map_colorspace` 分支在跑完精确修复后，若
  `also_fix_review` 为真则再调用 `set_images_colorspace_noncolor` 应用候选名单。
- **`ANALYZER_OT_fix_normal_colorspace`**（灯光合成面板独立按钮）：同样加
  `also_fix_review`/`_review_candidates`/`invoke()`/`draw()`，逻辑跟上面一致，
  只是没有 `key` 分发判断（这个操作符本身就只做这一件事）。`invoke()` 没候选时
  直接 `execute()`，不弹窗，跟原有「点一下就修完」的体感一致。

两个入口共享 `fixes.py` 里同一套 `find_normal_named_review_images` /
`set_images_colorspace_noncolor`，不重复实现。

## 已知风险 / 待验证

- 未跑 GUI 实测，只过了 `python -m compileall -q .`。需要 F8 重载后核对：
  - 场景里存在「贴图名含 normal 但没接在 NORMAL_MAP 节点上、色彩空间不是
    Non-Color」的情况时，点两个入口都能弹出二次确认弹窗，列出候选贴图名；
  - 弹窗里勾选「一并改成 Non-Color」确认后，这些贴图色彩空间被正确改掉，
    report 里的追加数量跟实际一致；
  - 不勾选直接确认时，只有精确检测部分被修复，候选贴图保持原样；
  - 没有候选贴图时（比如场景里没有法线贴图，或所有法线贴图名字里都不含关键字），
    两个入口都不弹窗，直接执行完成——跟改动前的体感一致；
  - 工程分析「快速修复」列表里其它 27 个检查项（比如负缩放、清理孤立数据等）
    点击后依旧是原来的「点击即执行」，不受这次改动影响，重做面板（F6）不出现
    法线贴图相关的多余 UI。
  - 用户描述的复杂案例（贴图混合 Geometry Normal 后接进节点组内 Diffuse BSDF）
    实测走一遍，确认按名称能被启发式候选名单捕捉到。

## 追加（同日）：发现蛙灾侧已有同类逻辑 + 补上多跳回溯

用户追问"这个逻辑是只修改我这边的代码吗？没有修改蛙灾那边的代码？"，核对后发现
`core/synccheck.py`（蛙灾专属）里 `_scan_normal_images()` 早就有按名称的启发式
兜底（正则 `_NORMAL_NAME = re.compile(r"(normal|_nor(?:[_.\b-]|$)|_nrm|nor_?gl)", re.I)`，
扫描范围是全部 `bpy.data.images`），而且 `checks.py::check_normal_map_colorspace`
的文档注释写得很清楚：当年做别馆自包含实现时特意选择不搬这部分，理由是"避免独立
实现和原版行为在边界情况上悄悄分叉"。也就是说上面记录的实现刚好把当年舍弃的部分
加回来了，但用的是自定义关键字列表（`normal`/`nrm`/`norm`/`法线`，纯子串匹配）和
更窄的扫描范围（只扫材质节点树里的 TEX_IMAGE），跟蛙灾侧不完全一致——正是当年想
避免的那种分叉。

用户随后又指出另一个漏检场景："我 mix 了两张 normal 贴图，再连到 normalmap 节点，
这个也要加在一开始的扫描逻辑里的，递归下去求索"——精确检测（NORMAL_MAP 节点
Color 输入）目前只看直连的一跳，如果中间隔着 Mix/MixRGB 之类的节点，两张被混合
的贴图都会漏检。这是检测逻辑本身的单跳限制，蛙灾/别馆两边的精确检测都有同样的坑。

### 改动

1. **`core/analyzer/checks.py`**：新增 `_walk_back_tex_images(socket, depth=0,
   _max_depth=16)`，从一个输入插槽顺着 `links` 递归往前找所有能追溯到的
   `TEX_IMAGE` 贴图（支持任意层 Mix/Math/Reroute 中转，不跨节点组边界，深度上限
   只是防御性保护）。`check_normal_map_colorspace` 里 NORMAL_MAP 分支的单跳
   `for link in color_input.links` 改成调用这个函数，修复"混合两张法线贴图接进
   NORMAL_MAP 节点"的漏检。
2. **`core/analyzer/fixes.py`**：
   - `fix_normal_map_colorspace` 和 `_images_wired_into_normal_map_node` 都改成
     调用 `checks._walk_back_tex_images`，跟检测阶段共用同一套遍历逻辑。
   - `_NORMAL_NAME_HINTS`/`_looks_like_normal_name` 删掉自定义关键字列表，改成
     `_NORMAL_NAME_RE = re.compile(r"(normal|_nor(?:[_.\b-]|$)|_nrm|nor_?gl)", re.I)`
     ——跟 `core/synccheck.py` 的 `_NORMAL_NAME` 完全一致的正则。
   - `find_normal_named_review_images` 的扫描范围从"材质节点树里用到的 TEX_IMAGE
     节点"改成全部 `bpy.data.images`，跟蛙灾侧 `_scan_normal_images` 的按名称兜底
     扫描范围对齐。
3. **`core/synccheck.py`**（蛙灾专属，本次跨边界修改——原因：用户两次明确要求
   把这个逻辑同步到蛙灾侧；改动只扩大 `pond.normal_scan`/`pond.normal_fix` 的
   检测覆盖面，不改 idname/UI 结构，不影响另一模式行为；归属不变，不需要更新
   `模块归属标注.md`，仅在此记录跨边界修改）：新增同名 `_walk_back_tex_images`
   （自包含一份，因为这个文件不 import `core/analyzer`），`_scan_normal_images`
   的 NORMAL_MAP 分支改成调用它，修复同一个单跳漏检问题。
